Data Residency Is a Workflow Decision, Not a Procurement Clause

New self-service regional controls make data residency a design choice inside AI workflows. Leaders need to map each data path, not rely on a contract label.

By R Koushik, NetworkGain Consulting

NetworkGain Point of View

New self-service regional controls make data residency a design choice inside AI workflows. Leaders need to map each data path, not rely on a contract label.

Data residency used to sit near the end of an AI buying process.

Legal asked where a provider stored data. Procurement reviewed the contract. Security checked the supplier assessment. The project team then began to build.

That order is now too late.

AI platforms are making regional choices available inside the product. On November 18, OpenAI said that eligible API organisation owners can select regional data residency when they create a project. Its guidance describes two patterns: a fixed regional project, or a Global project that can use regional processing for supported requests. It also tells users to check whether an option covers storage only or both storage and processing. OpenAI’s project guidance is clear on one important point: a fixed region selected during project creation cannot later be changed; a different region requires a new project.

This is a useful signal for every enterprise, whether it uses OpenAI, another provider or an internal model platform.

NetworkGain analysis: Data residency is no longer only a supplier attribute. It is a workflow decision. The decision affects project structure, request routing, keys, logs, tools, storage, support access, retention and the evidence that a team can produce later.

The contract still matters. It does not replace architecture.

The verified signal: regional controls are moving into project design

Verified fact: OpenAI’s November 18 release notes say that eligible API organisation owners can choose self-service regional data residency when they create a project. The release notes say that users can select an available fixed region or enable per-request residency on a new Global project. They also say that the option does not need a separate Zero Data Retention application.

Verified fact: OpenAI’s project documentation says that a fixed regional project uses its own settings. It instructs customers to check whether the selected option covers storage only or storage and processing. For a Global project with per-request residency, the documentation says to use a supported regional API hostname for each request that needs regional processing. It also says to confirm actual processing by checking the hostname and workload against the data-residency guidance.

Verified fact: The documentation names limits and dependencies. Not every region, model, endpoint or feature has the same availability. The region picker provides the options available at setup. Existing Global projects may be able to use per-request residency only if they already support it. UAE access requires a separate sales contact. These are platform details, not a universal data-residency standard.

This does not prove that one product solves an organisation’s sovereignty, privacy or regulatory duties. It does show that the architecture choices are becoming more granular. A team can no longer safely say, “The vendor is regional,” and end the analysis.

A region is not a single fact

Leaders often ask one question: “Where is the data?” That is the right instinct. It is not a complete question.

An AI workflow can have several data paths:

  • the original prompt or document;
  • retrieved data from a knowledge base;
  • model processing;
  • tool calls to other systems;
  • response data and temporary state;
  • logs, traces and error records;
  • backups, exports and human-support access;
  • a result copied into a downstream system.

Each path may have a different location, retention period, owner and access model. A regional inference endpoint does not automatically make every connected component regional. A contract clause does not show whether a specific request used the intended endpoint. A data-processing agreement does not tell a development team which project key to use on a particular workflow.

The important question is therefore more precise: For this workflow, where is each class of data stored, processed, transmitted and retained—and how can we prove it?

That is a technical and operating-model question. It needs legal, security, data and product teams to work from the same map.

Start with the business use case, not the provider menu

The cleanest design begins with the work itself.

Consider three examples. A marketing team may use public product copy to create campaign variants. A customer-service team may summarise account conversations. A product team may ask an AI system to search proprietary code, call an internal tool and propose a change. These workflows have different data classes, different consequences and different residency needs.

The correct regional setting may also differ. Some work may not need a regional restriction. Some may need fixed storage and processing in a named region. Some may need a global project with per-request routing because the user population or regulated data varies by market. Some may be unsuitable for an external AI service at all until the organisation changes the input, removes identifiers or builds a permitted environment.

There is no single “EU setting” or “India setting” that solves all of this. The team must state the data classification, the lawful and contractual basis, the required geography and the consequence if the workflow is routed wrongly.

This is why the decision cannot remain with procurement alone. Procurement can negotiate terms. Architecture must make the promised data path real.

Project boundaries should match control boundaries

When a provider offers regional controls at project creation, the project becomes a governance boundary. It can determine access, spend, keys, logs, rate limits and the region choices available to a workflow.

That suggests a practical design principle: do not group workloads only by department or budget code. Group them where they need different controls.

For example, an enterprise may need separate projects for:

  • public or low-sensitivity work that can use a standard global route;
  • regulated customer data that needs a fixed regional processing path;
  • a controlled pilot with strict access and short retention;
  • engineering work that can access code but cannot send customer data; and
  • evaluation work that uses synthetic or approved test data.

This does not mean every team needs its own project. Too many projects create their own access and observability problem. The unit of separation should be the control objective. If two workloads require the same data boundary, identity policy, model access and evidence, they may share a project. If they do not, sharing becomes a source of risk.

NetworkGain analysis: A project is not just an administrative folder. For AI, it can become the point where policy becomes enforceable: which keys exist, which models are permitted, which region is selected, which tools can run and which logs must be retained.

Runtime evidence is the missing control

Many AI programmes can show a policy document. Fewer can show evidence for a real request.

OpenAI’s guidance directs Global-project users to the supported regional hostname for a request that needs regional processing. It also says to check the actual hostname and workload. That is a useful operating pattern. A control should be visible at runtime, not only described at procurement time.

For every material workflow, teams should be able to answer these questions after an incident, an audit or a customer query:

  1. Which project and credential submitted the request?
  2. Which endpoint or routing rule did the workflow use?
  3. Which region covered storage, and which region covered processing?
  4. What input data, files or retrieved records were included?
  5. Which tools or downstream systems received data during the run?
  6. What logs, traces or temporary records exist, and how long do they remain?
  7. Did the workflow follow the intended route, and what happened if it could not?

The answer may come from provider logs, application telemetry, API gateways, identity records and data-catalogue metadata. It does not need to be a single new dashboard. It does need to be testable.

An organisation should test the exception path as carefully as the normal path. What happens when the required regional endpoint is unavailable? Does the application fail closed, queue the work, remove sensitive fields or silently fall back to a global route? The right answer depends on the use case. A silent fallback is rarely a good default for sensitive data.

Temporary data still belongs in the design

Teams often focus on the final answer and forget the work in progress.

This matters more as AI workflows become asynchronous. OpenAI’s background-mode documentation says that the service temporarily stores response data to run and retrieve a background request, including when the caller uses Zero Data Retention or sets store to false. The documentation says that the data is encrypted at rest during this temporary storage. That is an important safeguard. It is also a reminder that a simple “do not store” instruction may not describe the entire runtime path.

The same principle applies broadly. A workflow can create temporary prompts, tool outputs, embeddings, traces, cached instructions, retry records and error messages. Each item may be necessary for reliability. Each item should still have an owner, a purpose, a location and a retention rule.

Forward-looking inference: As regional controls become easier to select, customers and regulators will expect more precise answers about actual workflow behaviour. This is an inference from the direction of product design. It is not a claim about a particular legal requirement or provider roadmap.

The counterargument: regional controls can slow useful work

There is a fair counterargument. More regional projects, keys and routing rules can slow teams down. A central platform may already have strong contracts, encryption and access controls. Overly fine-grained design can create delays, duplicate data and a confusing developer experience. Not every internal summary needs the same control level as a regulated customer decision.

That is correct.

The purpose is not to turn every AI request into a cross-border legal review. It is to apply controls in proportion to the data and the consequence. Low-risk work should stay easy. High-risk work should not rely on an assumption that “the vendor handles it.”

Good architecture reduces this friction. A platform team can publish approved project patterns, automated policy checks, reusable client libraries and clear failure behaviour. Product teams can then choose a known pattern rather than inventing their own routing logic. The result is faster delivery with fewer hidden data paths.

Build a residency control map

CTOs, CIOs, chief data officers and security leaders can begin with a compact control map for material AI workflows. The map should include:

  1. Use case and owner: What business result does the workflow support, and who owns it?
  2. Data classes: What inputs, retrieval sources, tool outputs and logs can the workflow handle?
  3. Required geography: Is the requirement about storage, processing, support access, backup, transfer or all of these?
  4. Project and identity: Which project, key and access policy enforce the chosen boundary?
  5. Runtime route: Which endpoint, host or gateway rule must the application use?
  6. Exception behaviour: Does the workflow stop, queue, redact or fall back when the route is unavailable?
  7. Evidence: Which logs or records prove that the workflow followed the intended design?

This map should connect to existing privacy, security and architecture governance. It should not become another spreadsheet that nobody uses. The best test is practical: can the delivery team use the map to build a safe workflow, and can an accountable leader use it to explain what happened?

The NetworkGain view

Self-service regional controls are a quiet but important shift. They move data residency from a statement about a supplier to a choice inside the system that teams build.

The strategic response is not to collect more vendor assurances. It is to make the data path explicit. Classify the workload. Select the right control boundary. Route requests correctly. Record enough evidence to show what happened. Make failures visible and safe.

Leaders should ask:

  • Can we show where a material AI workflow stores and processes each important data type?
  • Does our project design reflect real control differences, or only organisational charts?
  • What happens when the required regional route is not available?
  • Do our tools, logs and retry paths follow the same residency policy as the main model call?
  • Can a product team use an approved pattern without becoming an expert in every provider setting?

Data residency is not a box to tick at procurement. It is a property that the workflow must maintain from the first input to the final action.
